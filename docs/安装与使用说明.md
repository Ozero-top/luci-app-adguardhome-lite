# AdGuard Home 助手（luci-app-adguardhome-lite）

面向 OpenWrt / ImmortalWrt / iStoreOS 的 LuCI 插件。保持系统原有 LuCI 风格，用一个页面完成“装内核、接 DNS、看状态”，所有核心操作不超过 3 步。

> 本文档包含：安装包选择、LuCI 上传安装、安装验证、三步上手、功能说明、常见问题、卸载回滚与维护说明。

---

## 1. 设计原则

- **零基础可用**：安装后打开插件，按“安装内核 → 一键启用 → 打开控制台”三步完成，不需要命令行。
- **不破坏原有 DNS**：安装时不会自动修改 DNS；只有点击“一键启用”才会接管。停止服务、卸载插件时自动恢复 DNSMasq 原始设置。
- **官方内核**：运行时优先从 AdGuard 官方 CDN 下载最新稳定版内核；国内用户可启用 GitHub 反代优先下载，反代失败自动回退官方 CDN 和 GitHub 直连。
- **配置可控**：常用设置提供中文说明；高级功能可直接编辑官方 `AdGuardHome.yaml`，保存前自动校验并保留备份。
- **中文引导内置**：插件内“使用引导”标签包含 DNS 模式说明、常用功能入口和故障排查提示。
- **独立 UI**：保留主题左侧导航；右侧插件页面通过 iframe 完全隔离主题 CSS/JS，固定浅色草绿 / 米黄。

## 2. 安装包选择与兼容性

`dist/` 下提供两个安装包，**同一个路由器只能安装其中一个**；25.12 及使用 `apk` 的固件不装包，改用 `install.sh`：

| 安装包 / 方式 | 适用固件 | 依赖 |
|---|---|---|
| `luci-app-adguardhome-lite_1.1.7-1_all.ipk` | OpenWrt 23.05 / 24.10、ImmortalWrt 24.10、iStoreOS 24.10 等使用新版 LuCI 的固件 | 自动安装 `luci-compat`、`curl`、`wget-ssl`、`ca-bundle` 等 |
| `dist/legacy/luci-app-adguardhome-lite_1.1.7-1-legacy_all.ipk` | OpenWrt 22.03 及更早的原生 Lua LuCI 固件 | 不依赖 `luci-compat` |
| `install.sh`（脚本安装） | OpenWrt / iStoreOS **25.12 及以后**（`apk` 包管理，无法安装 `.ipk`） | 脚本自动补齐 `luci-compat`、`luci-lua-runtime`、`curl`、`wget-ssl`、`ca-bundle` 等 |

判断方法：

- 在“系统 → 软件包”里能看到 `apk` 字样，或固件版本为 25.12 及以后：使用 **脚本安装**（见 4.1）。
- LuCI 界面为较新的卡片式界面，且“系统 → 软件包”中能搜索到 `luci-compat`：使用 **modern** 包。
- 固件版本为 22.03 或更早，软件包列表中没有 `luci-compat`：使用 **legacy** 包。

> 插件与旧版 `luci-app-adguardhome` 存在冲突，安装前请先卸载旧插件。
>
> 已测试内核：AdGuard Home **v0.107.80**（2026-11-08 官方最新稳定版）。插件会在安装/更新时自动获取最新稳定版，无需随内核版本频繁更新插件。

## 3. 安装前检查

1. 路由器已联网，且系统时间基本准确（HTTPS 下载依赖证书校验）。
2. 路由器剩余空间建议不少于 **50MB**（内核解压后约 30-40MB，具体取决于架构）。
3. 如果已安装旧版 `luci-app-adguardhome`，先在“系统 → 软件包”中卸载：
   - `luci-app-adguardhome`
   - `luci-i18n-adguardhome-zh-cn`
4. 如果旧插件正在运行，卸载后确认 `/etc/init.d/AdGuardHome` 已停止；必要时重启一次路由器。

## 4. 通过 LuCI 上传安装（推荐，一键完成）

1. 打开 LuCI：`http://路由器IP`
2. 进入 **系统 → 软件包**（部分固件叫“软件包管理”）。
3. 找到 **上传安装包 / Upload package**。
4. 选择对应版本的 `.ipk` 文件并上传安装。
5. 等待依赖自动安装完成。首次安装需要联网下载依赖。
6. 安装完成后，在 **服务** 菜单下会出现 **AdGuard Home 助手**。

> 如果已经安装过同版本的测试包，上传时若提示“已安装/无更新”，请先在软件包列表中卸载 `luci-app-adguardhome-lite`（配置、内核和数据会保留），再上传新包。
>
> 默认面板端口 `13800` 仅对**新安装**生效。已经安装过旧版的设备会保留原有 UCI 配置和端口；请在“基础设置”中把端口改为 `13800`，或删除 `/etc/config/adguardhome_lite` 后重新安装。
>
> 升级/重装时如果 UCI 中 `enabled=1`，安装脚本会自动重建开机自启链接并重启服务；面板通常会在约 10 秒内恢复。

如果上传界面提示依赖无法安装，请确认：
- 固件版本与安装包版本匹配（22.03 及更早请用 legacy 包）；
- 路由器可以访问 OpenWrt 软件源；
- 没有安装旧版 `luci-app-adguardhome`。

> 命令行安装仅作为备用方式（不是必需步骤）：
>
> ```sh
> opkg install /tmp/luci-app-adguardhome-lite_1.1.7-1_all.ipk
> ```
>
> 也可以使用离线自解压包（内含 modern 与 legacy 两个 ipk，自动选择）：
>
> ```sh
> sh /tmp/luci-app-adguardhome-lite_1.1.7-1.run
> ```

### 4.1 脚本安装（25.12 / apk 系统）

OpenWrt / iStoreOS **25.12 起默认使用 `apk` 包管理**，`.ipk` 无法安装。这类系统直接用 `install.sh`：脚本会自动下载源码、补齐依赖、安装文件并清理 LuCI 缓存，**不需要构建或下载安装包**。

```sh
# curl（推荐）
curl -fsSL https://raw.githubusercontent.com/Ozero-top/luci-app-adguardhome-lite/main/install.sh | sh

# 只有 wget 时
wget -qO- https://raw.githubusercontent.com/Ozero-top/luci-app-adguardhome-lite/main/install.sh | sh
```

国内网络访问 `raw.githubusercontent.com` 失败时，脚本本身也走反代：

```sh
curl -fsSL https://gh-proxy.org/https://raw.githubusercontent.com/Ozero-top/luci-app-adguardhome-lite/main/install.sh | sh -s -- -m https://gh-proxy.org
```

脚本会依次尝试 `gh-proxy.org`、`ghfast.top`、`gh-proxy.com` 和 GitHub 直连，哪一个能用就用哪一个；`curl` 与 `wget` 都支持。

常用参数：

| 参数 | 作用 |
|---|---|
| `-v 1.1.7` | 指定版本；`-v latest` 取最新 Release |
| `-m https://gh-proxy.org` | 指定反代，可重复 |
| `--no-deps` | 跳过依赖检查（依赖已装好时更快） |
| `--uninstall` | 卸载插件，恢复 DNSMasq 原始设置，保留配置与内核 |
| `--purge` | 卸载并删除 `/etc/config/adguardhome_lite`、内核与统计数据 |

```sh
# 卸载（保留配置与内核）
sh install.sh --uninstall

# 安装指定版本并指定反代
sh install.sh -v 1.1.7 -m https://gh-proxy.org
```

> 脚本安装不会在 `apk` 的已安装列表里留下记录，升级/卸载都请继续用 `install.sh`；重复安装时 `/etc/config/adguardhome_lite` 与内核都会保留。
>
> 25.12 首次安装后如果 LuCI 提示“未设置密码”，先在 LuCI 里设置管理员密码（或 SSH 执行 `passwd root`）再打开插件页面。这是 iStoreOS 自带的安全策略，与插件无关。

### 5.2 内核安装

- [ ] 点击“安装/更新内核”，进度框出现中文日志

如果下载失败，日志会显示具体阶段；常见原因是路由器无法访问外网、DNS 解析失败或空间不足。

### 5.3 一键启用

- [ ] 概览页第 2 步“一键启用”可点击
- [ ] 点击后服务状态变为“运行中”
- [ ] “DNS 接管”显示“接管 53 端口”
- [ ] 页面显示面板地址、管理员 `admin` 和默认密码 `admin123`
- [ ] SSH 执行 `nft list chain inet fw4 agh_dns_redirect` 能看到 `redirect to :53`（装了 OpenClash 时用来防止查询被劫持走）

### 5.4 面板与 DNS

- [ ] 点击“打开控制台”，能用默认密码登录 AdGuard Home
- [ ] 在 AdGuard Home“仪表盘”能看到查询统计
- [ ] 在局域网电脑上执行 `nslookup www.baidu.com 路由器IP` 能正常解析

### 5.5 可选：SSH 深度验证

```sh
# 插件 UCI 配置
uci show adguardhome_lite

# 服务状态
/etc/init.d/adguardhome_lite status

# 进程
pgrep -f AdGuardHome

# 上游：确认 DNSMasq 已不再自己解析（接管 53 时端口应为 1745）
uci get dhcp.@dnsmasq[0].noresolv        # 通常是 1
uci get dhcp.@dnsmasq[0].port            # 接管 53 时应为 1745
uci get dhcp.@dnsmasq[0].server          # 装了 OpenClash 通常是 127.0.0.1#7874

# 前置模式（clashfirst）：确认 Clash 上游已指向 AdGuard Home
uci get openclash.config.enable_custom_dns   # 应为 1
uci show openclash | grep dns_servers        # 应有一条 port=5335、ip=127.0.0.1

# 查看 DNSMasq 实际读取的 conf-dir 与插件转发文件
ls /tmp/dnsmasq.d/adguardhome-lite.conf 2>/dev/null

# 接管 53 + OpenClash：确认插件已把设备的 53 查询收回 53，而不是被 OpenClash 直送 1745/7874
nft list chain inet fw4 agh_dns_redirect   # 应为 redirect to :53
nft list chain inet fw4 dstnat | grep 'OpenClash DNS Hijack'   # 指向 53/1745/7874 都不影响

# DHCP 是否给设备下发了 IPv4 DNS（没有就补一条，见 9.2）
uci get dhcp.lan.dhcp_option             # 应包含 6,路由器IP

# 运行日志
logread | grep -i adguard
```

> 接管 53 端口模式下，`dhcp.@dnsmasq[0].port` 应为 `1745`，AdGuard Home 配置中的 DNS 端口为 `53`。如果同时开着 OpenClash，`dhcp.@dnsmasq[0].server` 通常仍是 OpenClash 设置的 `127.0.0.1#7874`，这样查询会继续交给 Clash 做 fake-IP 与分流。
>
> 注意别手动改成 `option server '...'`：这种单值写法会被生成脚本忽略，实际配置里不会出现 `server=`，结果是 DNSMasq 拿不到上游、全网解析失败。需要修改时用 `uci add_list`，或直接在插件里重新保存接管方式。

## 6. 三步上手

### 第 1 步：安装内核

1. 打开 **服务 → AdGuard Home 助手 → 概览**
2. 点击 **安装/更新内核**
3. 等待进度完成

插件会自动识别 CPU 架构（含 MIPS 大小端、ARM v5/v6/v7/v8、x86、RISC-V 等），从 AdGuard 官方 CDN 下载对应内核；失败会自动尝试 GitHub 直连。

国内网络如果访问 GitHub/官方 CDN 较慢，可先到 **基础设置** 把“GitHub 反代”设为 `gh-proxy.org` 等可用反代。启用后插件会优先通过反代下载 GitHub 内核，失败再回退官方 CDN 和 GitHub 直连。

### 第 2 步：一键启用

1. 点击 **一键启用**
2. 首次启用会从内置默认配置生成 `/etc/AdGuardHome.yaml`，并：
   - 使用默认账号 `admin` / 密码 `admin123`
   - 使用中文界面
   - 启用内置的 11 个过滤规则和 1 个白名单规则（含 AdGuard DNS、AdAway、AdRules、anti-AD、AWAvenue、GOODBYEADS、OISD Big、HaGeZi 等），并内置常见 DoH 服务的拦截规则
   - 查询日志与统计数据保留 30 天（查询日志只保存在内存，不写闪存）
   - 默认关闭 DNS 缓存、DNSSEC 和 fallback DNS，避免 Clash 的 fake-IP 被缓存、以及查询绕过代理
   - 默认采用“接管 53 端口”方式接管 DNS（DNSMasq 移到 1745）；装了 OpenClash 且开着 DNS 劫持/转发时，这个方式同样可用（详见第 8 节）
   - 将上游 DNS 指向 DNSMasq（`127.0.0.1:1745`），避免与 AdGuard Home 自身的 53 端口形成回环

### 第 3 步：打开控制台

1. 点击 **打开控制台**
2. 使用概览页显示的地址、账号、默认密码登录
3. 登录后即可在 AdGuard Home 面板中：
   - 启用/添加 DNS 黑名单
   - 打开安全搜索、家长控制
   - 修改上游 DNS
   - 查看查询日志和拦截统计

> 默认密码显示在概览页“运行状态”卡片中，可点击“显示/复制”。如果忘记密码，到“基础设置”页底部“修改面板密码”重设即可。

## 7. 功能说明

### 7.1 独立管理页面

- **保留 LuCI 主题自带的左侧导航栏和顶部区域**，不替换、不隐藏路由器原有菜单。
- 右侧插件页面通过 **iframe 独立渲染**，iframe 内不加载任何 LuCI 主题 CSS/JS，因此布局、卡片、字体和配色不会被 iStoreOS、ZeroWrt、Bootstrap 等主题影响。
- iframe 高度会随内容自动撑开，**右侧页面内部不显示垂直滚动条**；上下滚动由外层 LuCI 主题页面负责。
- 右侧固定为**浅色草绿 / 米黄**配色（草绿主色 `#4f7d3a`，米黄背景 `#f3eddf`），不提供深色切换。
- 右侧顶部标签：**概览 / 基础设置 / 高级配置 / 运行日志 / 使用引导**。
- 页面通过 LuCI 会话鉴权，iframe 与 LuCI 同源，接口仍受 ACL 和 CSRF Token 保护。

### 7.2 概览

- **运行状态**：服务状态、内核版本、DNS 接管方式、更新通道、GitHub 反代、面板地址、管理员、面板密码、配置文件、工作目录
- **过滤统计**：直接读取 AdGuard Home 的统计接口，无需打开控制台即可看到 **DNS 查询 / 已拦截（广告、跟踪）/ 恶意·钓鱼 / 成人内容（家长控制）**，随状态每 10 秒自动刷新
- **三步完成配置**：安装内核、一键启用、打开控制台
- **服务控制**：启动、停止并关闭自启、重启
- **新手提示**：常见场景与故障入口

### 7.3 基础设置

| 设置项 | 说明 |
|---|---|
| 启用 AdGuard Home | 开启后启动服务；关闭后停止并恢复 DNSMasq 原始设置 |
| DNS 接管方式 | 大白话：**想在 AdGuard Home 里看到每台设备的 IP → 选“接管 53 端口”，装了 OpenClash 开着 DNS 劫持/转发也照样能用**；**不想让 AdGuard Home 占 53、只想要过滤 → 选“OpenClash 前置”**。其余两种只在特殊情况用，详见第 8 节；切换时只调整插件内置上游，自定义上游保持不变。保存时会自动写入适合 Clash fake-IP 的参数（关闭缓存、关闭 DNSSEC、并行上游） |
| 管理面板端口 | 默认 13800；不能使用 53、1745、5333、5335 等 DNS 预留端口 |
| 内核安装位置 | 内置存储重启保留；内存临时适合小闪存，重启后需重新安装 |
| 数据工作目录 | 内置存储保留统计和过滤缓存；内存临时减少闪存写入，但重启后统计清空 |
| 内核更新通道 | 稳定版 / 测试版 |

| 当前状态 | 显示内核版本与运行状态 |
| 修改面板密码 | 浏览器本地计算 bcrypt 哈希，保存后自动重启服务 |

## 8. DNS 接管方式：什么情况用哪种

先记住两句话：

- **想看到每台设备、让所有域名都先过一遍过滤 → 选「接管 53 端口」**。哪怕 OpenClash 开着「DNS 劫持」也可以：插件会把设备的 DNS 请求统一收回路由器 53 端口，最后照样落到 AdGuard Home。
- **不想让 AdGuard Home 占 53 端口，或不需要逐设备统计 → 选「OpenClash 前置」**。

为什么「接管 53」能和 OpenClash 共存？把 OpenClash 的两件事拆开看就明白了：

- **DNS 劫持**：nftables 把设备的 DNS 请求（哪怕设备自己设了 `8.8.8.8`）拽回路由器，目标端口各固件不同，常见 `redirect to :53`，也有写 `:1745` 或 `:7874` 的。插件自建的 `agh_dns_redirect` 链会先一步收回 `53`，所以三种写法都不影响过滤。
- **DNS 转发**：OpenClash 把 DNSMasq 的上游改成 **`127.0.0.1#7874`**，也就是交给 Clash DNS 去解析。

于是 53 交给 AdGuard Home 之后，完整链路是：

```
设备 → OpenClash 劫持收回 53 → 53 AdGuard Home（过滤、记设备 IP）
     → 1745 DNSMasq → 7874 Clash DNS（fake-IP、分流）→ 真实 DNS
```

过滤、逐设备统计、Clash 的 fake-IP 与分流，三样都在。

「接管 53 端口」模式会创建一条独立的 nft 链，把局域网设备的 53 查询在 OpenClash 劫持之前收回路由器 53 端口，所以无论 OpenClash 的规则指向 `:1745` 还是 `:7874`，查询都会先进入 AdGuard Home。检查命令：

```sh
nft list chain inet fw4 agh_dns_redirect
```

看到 `redirect to :53` 的规则即为正常；如果这条链不存在，重新在插件里保存一次「接管 53 端口」即可。

### 8.1 照着你的情况选（一张表搞定）

| 你的情况 | 选哪个 | 大白话原因 |
|---|---|---|
| 装了 OpenClash（DNS 劫持/转发开着），还想看到每台设备 | **接管 53 端口** | 插件先把查询收回 53，交给 AdGuard Home 过滤，再经 DNSMasq → Clash 分流 |
| 没装 OpenClash | **接管 53 端口**（默认） | 最直接：所有设备默认都走它，过滤和统计最完整 |
| 装了 OpenClash，但不想让 AdGuard Home 占 53，也不在乎逐设备统计 | **OpenClash 前置** | 让 Clash 把查询交给 AdGuard Home，AGH 只看到 `127.0.0.1` |
| 不想让 AdGuard Home 占 53，但也没人抢 53 | **DNSMasq 上游** | DNSMasq 留在 53，收到查询后转给 AdGuard Home（5333）过滤 |
| 只想看看面板，或 DNS 已经由别的程序管了 | **仅面板模式** | 什么都不改，只开 13800 管理面板 |

> 「OpenClash 串联」已下线：OpenClash 写入的 `server=127.0.0.1#7874` 排在 `conf-dir` 之前，`strict-order` 下查询会被 Clash 抢先应答，AdGuard Home 实际收不到查询。旧配置在保存或启动时会自动迁移为「接管 53 端口」。

### 8.2 每种方式的大白话说明

**① 接管 53 端口（默认，推荐）**

- **什么时候用**：想看到每台设备、让所有域名都先过一遍过滤。没装 OpenClash 直接用；装了 OpenClash 且开着 DNS 劫持/转发，也能直接用。
- **查询怎么走（没装 OpenClash）**：设备 → 53 端口 AdGuard Home（过滤）→ 1745 端口 DNSMasq → WAN 下发的上游 DNS。
- **查询怎么走（装了 OpenClash）**：设备 → OpenClash 劫持收回 53 → 53 端口 AdGuard Home（过滤，记录真实设备 IP）→ 1745 端口 DNSMasq → 7874 端口 Clash DNS（fake-IP、分流）→ 真实 DNS。
- **要注意**：和 OpenClash 一起用时，Clash 必须保持运行（DNSMasq 的上游指向 7874）；Clash 停了会解析失败，这与 OpenClash 本身的行为一致。插件会自建 `agh_dns_redirect` 链把设备的 53 查询收回 53，所以 OpenClash 劫持指向哪里都不影响过滤，检查方法见第 8 节开头。

**② DNSMasq 上游**

- **什么时候用**：你不想让 AdGuard Home 占 53 端口，同时又没有程序抢 53。
- **查询怎么走**：设备 → 53 端口 DNSMasq → 5333 端口 AdGuard Home（过滤）→ 自动选择的上游 DNS。
- **要注意**：检测到 Clash 在运行时会优先把上游交给 Clash；只有劫持规则直接指向 7874 时才会被绕过，指向 `:53` 时正常。

**③ OpenClash 串联（已下线）**

早期版本提供过这个模式：AdGuard Home 监听 5333，DNSMasq 通过 `conf-dir` 把查询转给它。实际环境中 OpenClash 会把 `server=127.0.0.1#7874` 写进 DNSMasq 的主配置，且排在 `conf-dir` 之前，`strict-order` 下 Clash 先应答，AdGuard Home 收不到查询；OpenClash 每次启动还会重写这条上游。因此该模式已移除，选择过它的配置会自动迁移为「接管 53 端口」。

**④ OpenClash 前置（不需要逐设备统计时选它）**

- **什么时候用**：不想让 AdGuard Home 占 53 端口，或者只关心过滤、不关心每台设备各自查了什么；也适合「接管 53」被某些固件的劫持规则挡住时作为备选。
- **查询怎么走**：设备 → OpenClash 劫持到 7874 端口 Clash DNS → 5335 端口 AdGuard Home（过滤）→ 真实 DNS（运营商或公共 DNS）。
- **插件会自动做什么**：开启 OpenClash 的“自定义 DNS”，新增一条 `127.0.0.1:5335` 的上游，暂时禁用其它上游，并关闭“追加 WAN DNS”，避免 Clash 自己偷偷去问运营商 DNS 把查询绕过去。原来的值会记下来，停止或切换时还原。
- **要注意**：Clash 内核必须运行；OpenClash 重启、更新或重新“一键设置”后，自定义上游可能被重置，回插件重新保存一次「OpenClash 前置」即可。这个模式下面板里看到的来源都是 Clash（`127.0.0.1`），看不到每台设备的名字，属于正常现象。由于来源只有一个地址，插件会把回环地址（`127.0.0.1`、`::1`）加入 AdGuard Home 的限速白名单（`ratelimit_whitelist`），否则超过 20 qps 会被限速。另外 Clash 的 fake-IP 会对所有 A 记录返回 `198.18.x.x`，AdGuard Home 的拦截结果在 DNS 层不会显示成 `0.0.0.0`，实际拦截发生在连接阶段；想要确定的拦截效果和逐设备统计，请用「接管 53 端口」。

**⑤ 仅面板模式**

- **什么时候用**：只想先看看界面，或者你已经有别的 DNS 方案（例如另一台软路由、Pi-hole）。
- **结果**：完全不动系统 DNS，只保留 13800 管理面板。

### 8.3 切换、停止、卸载时会怎样

- **切换方式不会越配越乱**：插件会先把 DNSMasq 恢复成接管前的原值，再按新方式配置。
- **只恢复你原来的设置**：接管前会记下 DNSMasq 的端口、`noresolv`、`resolvfile` 和 `server`，停止/卸载时按原值写回，不会偷偷写入 `223.5.5.5` 之类的公共 DNS。
- **DNSMasq 不会跟着劫持端口跑**：「接管 53」模式下 DNSMasq 固定移到 1745，其它模式留在 53，绝不会去抢 Clash 的 7874（那样会导致 DNSMasq 起不来、全网断 DNS）。
- **怎么确认没被绕过**：先看插件自建的 `nft list chain inet fw4 agh_dns_redirect`，有 `redirect to :53` 就说明查询一定会进 AdGuard Home；只有这条链缺失、且 OpenClash 劫持直接指向 `:7874` 时才会被绕过。
- **上游失效自动回退**：恢复后发现原来的本地上游已经没进程监听（例如 Clash 已停止），会自动改用 WAN 下发的 DNS 并重启 DNSMasq。
- **解析自检**：恢复完成后会做一次解析测试，失败会写进运行日志。

### 8.4 四条最容易踩的坑

- **别让两边的上游互相指**：前置模式的上游必须是真实 DNS；把「接管 53」切到「前置」时，插件会先把 Clash 的上游还原，否则会形成查询环、直接上不了网。
- **「接管 53」+ OpenClash 可以共存，不用管劫持目标**：插件自建的 `agh_dns_redirect` 链在 OpenClash 规则之前生效，`redirect to :53`、`:1745`、`:7874` 的写法都会先落到 AdGuard Home。
- **Clash 停掉时这套组合也会解析失败**：因为 DNSMasq 的上游指向 7874，Clash 不在就没人解析。只想要过滤、不想受 Clash 影响时，可以选「OpenClash 前置」（它的上游是真实 DNS）。
- **手动设了 `8.8.8.8` 的设备**：「接管 53」会把局域网设备的 53 查询（含 IPv4/IPv6）收回路由器，所以仍然会经过 AdGuard Home；但手机自带的“私人 DNS”（DoT/DoH）仍会绕过，需要另行拦截 853/加密 DNS 域名。

### 8.5 开机启动顺序（不需要手动干预）

| 阶段 | 服务 | 初始化序号 | 作用 |
|---|---|---|---|
| 1 | DNSMasq | START=19 | 先提供本地 DNS/DHCP；「接管 53」时它在 1745 待命 |
| 2 | AdGuard Home | START=95 | 占住 53（接管 53）或 5335（前置），并完成接管配置 |
| 3 | OpenClash | START=99 | 最后启动，开启 53 劫持并把上游交给 AdGuard Home |

这样排序的原因：OpenClash 的 DNS 配置里写着「上游 = 127.0.0.1:5335」，如果它比 AdGuard Home 先起来，开机阶段会出现一段解析失败；反过来，AdGuard Home 的上游在接管 53 时指向 DNSMasq 的 1745，DNSMasq 又先于它启动。因此按 `DNSMasq → AdGuard Home → OpenClash` 的顺序，每个环节依赖的端口都已经就绪。

插件安装/启用时会自动注册 `/etc/init.d/adguardhome_lite`（`START=95`、`STOP=01`），无需手工执行 `enable`。

## 9. 常见问题

### 9.1 内核下载失败

- 确认路由器能访问外网，DNS 正常。
- 确认系统时间准确（HTTPS 证书校验依赖时间）。
- 国内网络可在“基础设置”中切换 `GitHub 反代`（例如 `gh-proxy.org`）；启用后优先通过反代下载，反代不可用再回退官方 CDN 和 GitHub 直连。
- 如果路由器使用 OpenClash / Clash 等 fake-IP DNS（域名解析到 `198.18.x.x`），插件会自动通过公共 DNS 获取真实 IP，并用 `curl --resolve` 下载，无需关闭代理或修改路由。
- 内置过滤规则部分使用 `raw.githubusercontent.com`，国内网络可能下载较慢或失败；可在 AdGuard Home 面板改用国内镜像/反代地址，或先删除该规则后重新添加。
- 测试版只使用官方 beta 通道，不走 GitHub 反代，避免误装稳定版。
- 查看概览页进度日志或“运行日志”。
- 空间不足时，到基础设置把内核位置改为“内存临时”，或清理闪存。

### 9.2 启用后局域网不能上网

1. 打开概览页，点击 **停止并关闭自启**。
2. 插件会自动恢复 DNSMasq 原始设置；多数情况下立即恢复。
3. 如果同时运行 OpenClash，插件会把 DNSMasq 恢复成接管前 OpenClash 设置的样子（通常是 53 端口、上游指向 Clash 的 7874），不会因为关闭插件而断开代理 DNS。
4. 如果仍不能上网，可通过 SSH 执行：

```sh
/etc/init.d/adguardhome_lite stop
/etc/init.d/dnsmasq restart
```

5. 查看“运行日志”，重点确认：
   - 内核是否存在
   - 配置是否被改坏
   - 53/1745/5333/5335 端口是否被其他程序占用

6. 如果路由器自己解析正常、但某台设备（尤其 Windows）打不开网页，通常是设备没拿到 IPv4 DNS（`ipconfig /all` 里 DNS 一栏为空，或只剩无效的 `fec0::` IPv6 地址）。在路由器上补一条 DHCP 下发：

```sh
uci add_list dhcp.lan.dhcp_option='6,192.168.100.254'   # 换成路由器实际的 LAN IP
uci commit dhcp
/etc/init.d/dnsmasq restart
```

然后让设备断开重连（Windows 可执行 `ipconfig /renew`），确认 `nslookup www.baidu.com` 能解析。

> 也可以直接在系统网络设置里手动把 DNS 设为路由器 IP 应急，但补 DHCP 下发才能让所有设备自动生效。

### 9.3 面板端口被占用

到“基础设置”把管理面板端口改为 `3001` 等，保存后使用新端口访问。

### 9.4 重启后内核消失

说明内核安装在 `/tmp/AdGuardHome/AdGuardHome`（内存临时位置）。重新到概览页点击“安装/更新内核”，或把安装位置改为内置存储。

### 9.5 忘记面板密码

到“基础设置”页底部“修改面板密码”，输入新密码并保存。无需知道旧密码。

### 9.6 升级 OpenWrt 固件后

- `/etc/AdGuardHome.yaml` 和过滤缓存会保留；
- 内核文件较大，不进入固件备份，升级后需重新点击“安装/更新内核”；
- 如果服务未自动启动，到基础设置重新保存一次或重新启用。

### 9.7 从旧版插件迁移

1. 卸载旧版 `luci-app-adguardhome` 和中文语言包。
2. 确认旧服务已停止。
3. 安装本插件。
4. 如果保留 `/etc/AdGuardHome.yaml`，本插件会直接使用它；第一次启用时会同步面板端口和 DNS 端口。
5. 旧版使用的工作目录可能不同，过滤器缓存/统计不会自动迁移，AdGuard Home 会重新下载过滤器。

### 9.8 与旧插件冲突

安装包内置 `Conflicts` 声明，检测到旧版 `luci-app-adguardhome` 时会拒绝安装。请先卸载旧版再安装。

### 9.9 如何确认当前架构

概览页的安装日志会显示识别结果，例如 `amd64`、`arm64`、`mipsle_softfloat`。如果提示架构不支持，请查看“运行日志”中的设备架构信息。

> 支持：x86_64/386、ARM64、ARM v5/v6/v7/v8(32位)、MIPS/MIPSel/MIPS64/MIPS64el、RISC-V 64、PPC64LE。暂不支持 LoongArch。

### 9.10 点击“停止并关闭自启”无效

- **停止服务后面板也会关闭**，这是正常行为；需要面板时请重新“启动服务”。
- 先确认插件本身完整安装：SSH 执行 `ls /etc/init.d/adguardhome_lite`。如果文件不存在，说明插件未安装或安装不完整，请重新上传 ipk。
- 正常停止会同时结束进程、恢复 DNSMasq 并删除开机自启链接；日志在“运行日志”或 `/var/run/adguardhome_lite_action.log`。
- 1.0.0-1 已增加残留进程强制清理：如果 procd 未成功结束进程，插件会自动 `kill` 并确保端口释放。
- 停止成功后页面会自动刷新显示“已停止”；如果页面仍显示运行中，手动刷新一次即可。
- 仍无法停止时，可 SSH 执行：

```sh
/etc/init.d/adguardhome_lite stop
killall -9 AdGuardHome 2>/dev/null
```

### 9.11 修改面板端口后 13800 打不开

- 修改端口后插件会停止并重启内核，请等待约 5-10 秒再访问。
- 只有服务处于“运行中”时面板才会监听；已停止状态下面板打不开是正常的。
- 升级/重装插件后如果服务未恢复，点击“启动服务”；新版本安装脚本会根据 UCI `enabled=1` 自动重建自启并重启。
- 确认 UCI 和配置一致：

```sh
uci get adguardhome_lite.main.webport          # 应为 13800
grep -m1 '^  address:' /etc/AdGuardHome.yaml   # 应为 0.0.0.0:13800
netstat -lnt | grep 13800
```

- 旧版安装会保留原来的 UCI 端口（可能是 3000），需要在“基础设置”改成 13800，或删除 `/etc/config/adguardhome_lite` 后重新安装。
- 如果端口仍被旧进程占用，插件的强制清理逻辑会处理；也可以执行 `/etc/init.d/adguardhome_lite restart` 后重试。

### 9.12 同时运行 OpenClash 时，去广告不生效

**现象**：AdGuard Home 状态正常、过滤器规则已加载，但查询统计里拦截数为 0，广告域名仍能正常解析。

**原因（先分两种情况）**：

- OpenClash 的劫持规则直接指向 `:7874`，且没有「接管 53」的收回规则：查询进了 Clash DNS，AdGuard Home 一条都收不到，所以拦截数为 0。
- 用的是「OpenClash 前置」：过滤其实生效，但查询是 Clash 转发来的，来源全是 `127.0.0.1`，看起来像“没有客户端”。

**处理方式一（推荐，过滤 + 逐设备统计都要）：接管 53 端口**

在插件 **基础设置 → DNS 接管方式** 中选择 **“接管 53 端口”** 并保存。插件会自动：

- 让 AdGuard Home 监听 `53`，客户端查询直接落在它这里（能看到真实设备 IP）
- 把 AdGuard Home 上游设为 `127.0.0.1:1745`（DNSMasq），PTR 反向解析也走 1745
- 把 DNSMasq 移到 `1745`，并保留 OpenClash 原来的上游（通常是 `127.0.0.1#7874`）

链路为：客户端 → OpenClash 劫持收回 `53` → `53` AdGuard Home（过滤）→ `1745` DNSMasq → `7874` Clash DNS（fake-IP/分流）→ 真实 DNS。

前提：保持「接管 53 端口」模式（插件会自动创建 `agh_dns_redirect` 链把查询收回 53），Clash 内核保持运行：

```sh
nft list chain inet fw4 agh_dns_redirect   # 应为 redirect to :53
```

如果这条链不存在，查询就可能被 OpenClash 的规则直送 `:1745`/`:7874` 而跳过 AdGuard Home，请重新保存一次「接管 53 端口」，或改用下面的「OpenClash 前置」。

**处理方式二（不需要逐设备统计）：OpenClash 前置**

在插件 **基础设置 → DNS 接管方式** 中选择 **“OpenClash 前置”** 并保存。插件会自动：

- 让 AdGuard Home 监听 `5335`
- 把 AdGuard Home 上游设为真实 DNS（WAN 下发优先，其次公共 DNS），不会指向 Clash，避免查询环
- 开启 OpenClash 的“自定义 DNS”（`enable_custom_dns=1`），新增 `127.0.0.1:5335` 的 nameserver，并暂时禁用其它 nameserver（停止/切换时恢复原值）
- 在 Clash 运行中时重启 OpenClash，使新上游立即生效

链路为：客户端 → OpenClash 劫持 → `7874` Clash DNS → `5335` AdGuard Home（过滤）→ 真实 DNS。

前提：OpenClash 的 DNS 劫持必须开启（`enable_redirect_dns` 为 `1` 或 `2`），且 Clash 内核正在运行。

**还想让 Clash 决定域名怎么解析**：请用「接管 53 端口」——查询先由 AdGuard Home 过滤，再经 DNSMasq（1745）交给 Clash（7874）做 fake-IP 与分流，既保留分流也能逐设备统计。原来的「OpenClash 串联」已下线（DNSMasq 会优先命中 Clash 的上游，过滤实际不生效）。

**手动检查/补救**（自动化失败时）：

```sh
uci get openclash.config.enable_custom_dns     # 应为 1
uci get openclash.config.enable_redirect_dns   # 应为 1 或 2
uci show openclash | grep dns_servers          # 应有一条 ip=127.0.0.1、port=5335
```

也可在 OpenClash 面板“覆写设置 → DNS 设置 → 自定义上游 DNS”中添加 `127.0.0.1:5335`（UDP），并只保留这一条。

**验证**：

```sh
nslookup pos.baidu.com 路由器IP    # 「接管 53」下应返回 0.0.0.0；前置模式会显示 198.18.x.x fake-IP（正常）
nslookup www.baidu.com 路由器IP    # 应正常解析
nslookup www.google.com 路由器IP   # 代理站点应返回 198.18.x.x fake-IP
```

> OpenClash 更新或重新执行“一键设置”后可能重置自定义上游；重新保存一次「OpenClash 前置」即可恢复。

### 9.13 关闭插件后发现 DNS 配置被改 / 无法解析

插件停止时只会写回接管前记录的原值，不会写入 `223.5.5.5`。如仍异常，按顺序检查：

```sh
# 1. 查看 DNSMasq 当前设置
uci show dhcp | grep -E 'port|server|noresolv|resolvfile'

# 2. 查看 OpenClash 是否仍在劫持 53
nft list chain inet fw4 dstnat | grep 'OpenClash DNS Hijack'

# 3. 测试解析
nslookup www.baidu.com 127.0.0.1
nslookup www.baidu.com 路由器IP
```

- 正常情况下：不接管时 DNSMasq 监听 `53`；「接管 53」时 DNSMasq 在 `1745`、AdGuard Home 在 `53`；
- 「接管 53」时先看 `agh_dns_redirect` 链：存在就会被收回 53，OpenClash 劫持目标写 `53`、`1745`、`7874` 都不影响；
- OpenClash 劫持直接指向 `7874` 且没有这条链，说明查询由 Clash 接管（前置模式），「接管 53」下则会被绕过；
- 如果 OpenClash 已停止，DNSMasq 仍应监听对应端口，且不应再指向 `7874`，否则会解析失败；
- 如端口或上游不一致，在“基础设置”重新保存对应接管方式，插件会自动修正。

### 9.14 开启「安全浏览」后解析变慢或失败

AdGuard Home 的「安全浏览」（拦截恶意/钓鱼网站）依赖 `family.adguard-dns.com` 在线服务。国内网络直连不可达时，每次查询都要等它超时，表现为解析很慢、甚至完全失败（日志里会出现大量 `context deadline exceeded`）。

处理方式：到 AdGuard Home 面板「过滤器 → 常规」关闭「安全浏览」，或直接改配置：

```sh
sed -i 's/^  safebrowsing_enabled: true/  safebrowsing_enabled: false/' /etc/AdGuardHome.yaml
/etc/init.d/adguardhome_lite restart
```

关闭后「恶意/钓鱼」统计会一直是 0。插件默认不开启它，正是为了避免这个问题；「成人内容」统计来自家长控制，同样需要手动开启后才会有数据。

### 9.15 过滤规则一直更新失败（rules_count 为 0）

国内直连 `raw.githubusercontent.com` 常被重置。插件在保存设置时会自动检测 OpenClash 的 HTTP 代理端口（`openclash.config.http_port`，常见 7890），并写入 AdGuard Home 的 `http_proxy`，让规则下载走代理：

```sh
grep -n '^http_proxy' /etc/AdGuardHome.yaml      # 应形如 "http://127.0.0.1:7890"
curl -s -u admin:admin123 http://127.0.0.1:13800/control/filtering/status | grep -A2 nsfw
```

如果显示为空，说明 Clash 未运行或 HTTP 端口未监听；启动 OpenClash 后重新保存一次设置即可。

## 10. 安全建议

- AdGuard Home 面板默认对局域网开放，请勿把 13800 端口映射到公网。
- 默认密码为 `admin123`，建议首次登录后通过“基础设置 → 修改面板密码”更换。
- “接管 53 端口”会调整系统 DNSMasq，若路由器上还有 Pi-hole、AdGuard Home 旧实例、自建 DNS 等服务，请先确认端口不冲突。
- 高级配置会直接修改官方 YAML，建议修改前先复制备份。
- 通过 HTTP 访问 LuCI 时，管理员密码和面板密码均在局域网内传输；对安全要求高的环境请为 LuCI 启用 HTTPS。

## 11. 卸载与回滚

### 11.1 正常卸载

在 LuCI **系统 → 软件包** 中卸载 `luci-app-adguardhome-lite`。25.12 / `apk` 系统的脚本安装没有包记录，改用 `sh install.sh --uninstall`（彻底清理加 `--purge`）。

卸载过程会自动：
- 停止服务
- 恢复 DNSMasq 原始设置
- 取消开机自启

默认保留：
- `/etc/config/adguardhome_lite`
- `/etc/AdGuardHome.yaml`
- `/etc/AdGuardHome/`（统计、查询日志、过滤器缓存）
- 内核文件 `/usr/bin/AdGuardHome/AdGuardHome`

这样重新安装时可以继续使用原配置和统计。

### 11.2 彻底清理（可选，SSH）

```sh
opkg remove luci-app-adguardhome-lite
rm -f /usr/bin/AdGuardHome/AdGuardHome
rm -rf /etc/AdGuardHome
rm -f /etc/AdGuardHome.yaml
```

> 该操作会删除配置、统计和过滤缓存，请先确认不再需要。

### 11.3 回滚到旧版插件

1. 卸载本插件（会自动恢复 DNS）。
2. 安装旧版 `luci-app-adguardhome`。
3. 旧版会读取 `/etc/AdGuardHome.yaml`；如端口/工作目录不同，请在旧版设置中调整。
